## 5b26872 — discard
**Source:** agent
**Change:** Re-added just the windowed truncated-BPTT loader (`TRAIN_SEQ_LEN=128`, `WINDOW_BATCH_SIZE=256`) and learned `(h0, c0)` initial state from the reverted 5fc6b30 bundle, this time holding `LEARNING_RATE=0.003`, `WEIGHT_DECAY=0.0`, `EMBED_SIZE=128` at run e980c7a's already-confirmed values, to isolate whether the loader/init-state change alone helps.
**Result:** val_bpb 1.447791 (vs. e980c7a's 1.441281 — a wash, technically 0.0065 worse), top1 0.6839, top5 0.9373, memory 0.8GB, 10030 steps, 328.3M tokens (comparable to e980c7a's 335.5M — not a throughput-exposure confound either way), 0.290M params
**Notes:** Clean isolation this time (single conceptual change vs. the bundle), and the answer is clear: no win, plus real code complexity (a whole new dataloader function). Simplicity criterion says discard. The deeper insight (the "surprise" worth keeping): baseline-improve's windowed loader was RNN's single biggest win because it let the RNN avoid backpropagating through up to 1024 steps of vanishing gradient. But the run-3 whole-tune loader already gives the LSTM up to `MAX_SEQ_LEN=1024` of real context per tune — chopping to `seq_len=128` windows does not lengthen that, it *shortens* it (1024 → 128), and doesn't even clearly improve throughput here (328M vs 335M tokens, roughly the same). So windowing solves a vanilla-RNN-specific problem (long-BPTT vanishing gradient) that the LSTM's gates don't have in the same way, and simply trades context length for constant-length batching with no measured benefit. Reverting (`git reset --hard` to e980c7a-branch tip 1156e1d). Next: test the actually LSTM-specific lever program.md flags — **stateful** windowing (carry `(h, c)` across a tune's windows in order, instead of resetting to the learned `(h0, c0)` every window) — this keeps the windowed loader's fixed-length batching/throughput shape but could restore the lost cross-window context for a cell type whose whole point is retaining it.

## fa8245a — keep
**Source:** agent
**Change:** Added `make_stateful_windowed_dataloader`: `WINDOW_BATCH_SIZE=256` parallel lanes, each stepping sequentially through one tune's tokens in consecutive `TRAIN_SEQ_LEN=128` chunks (no shuffling within a tune), yielding a `reset_mask` when a lane starts a new tune. `CharRNN.forward` gained an optional `init_state` kwarg and a `self.last_hidden` (detached) side channel so the training loop can thread `(h, c)` across steps — `torch.where(reset_mask, learned_(h0,c0), carried_(h,c))` — without changing `forward`'s public signature (`quick_eval`/`evaluate_bpb` untouched, still get fresh learned-`(h0,c0)` full-sequence evaluation). Detached truncated BPTT: gradient horizon per step stays at 128, but forward-pass context now persists across a tune's own windows. `LEARNING_RATE=0.003`, `WEIGHT_DECAY=0.0`, `EMBED_SIZE=128` held at run e980c7a's confirmed values — the only new variable vs. run 5b26872 (discarded stateless windowing) is the state carry itself.
**Result:** val_bpb 1.395289 — new best, beating e980c7a's 1.441281 by 0.046 and the RNN baseline (2.087648) by 33%. top1 0.6954, top5 0.9389, memory 0.8GB, 9254 steps, 302.9M tokens (82% of the keep-row median [335.5, 407.0] → 371.25 — above the 60% `keep-prov` threshold, not a throughput confound), 0.290M params
**Notes:** Confirms the hypothesis program.md flagged specifically for this worktree: baseline-improve found stateful windowing a wash for the vanilla RNN (median tune ~258 tokens, ~4 windows at seq_len=64, and the RNN's own ~10-50-step effective memory couldn't use the extra carried context anyway). Here, with an LSTM whose whole point is retaining long-range state through its gates, carrying `(h, c)` across a tune's ~2 windows (at seq_len=128) turns into a real, measurable win — the model gets effectively the same cross-window context as the whole-tune loader (run e980c7a) while paying for a shorter 128-step BPTT graph per update instead of up to 1024, at comparable token throughput. This is the clearest evidence yet in this worktree that the LSTM's cell-state memory is doing real long-range work, not just gating away vanishing gradients passively. **New working best config: hidden_size=128, embed_size=128, lr=0.003, wd=0.0, stateful windowed loader (seq_len=128, window_batch_size=256).** Natural next directions: sweep `TRAIN_SEQ_LEN` (256? fewer, bigger windows per tune) now that stateful carry is confirmed working, re-check `HIDDEN_SIZE` under this new loader's throughput profile, and eventually run the formal RNN-vs-LSTM ablation pair against `baseline-improve`'s best (1.526216) for the write-up.
